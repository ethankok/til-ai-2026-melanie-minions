1. What is AE?

AE (Autonomous Exploration) is one of the five competition tasks in TIL-AI 2026. It is a 6-team Bomberman-style grid environment where each team controls one agent on a 16×16 map, places bombs, collects items, and tries to maximize total reward over a fixed number of game steps. The Docker image we ship hosts an HTTP server; the official evaluator sends one observation per game tick (a JSON dict containing the agent's view, base view, scalars like health and step, plus an action_mask) and expects a single integer action back.

Scoring

  • Per-round score = total reward / 1000 (per the eval harness convention).
  • Reward components (per the official Wiki): collect_mission +5, collect_resource +2, collect_recon +1; damage_dealt +1/dmg; attack_kill +15; destroy_enemy_base +50; own_base_destroyed -50; damage_taken -1/dmg.
  • Cloud blended score = 0.75 × accuracy + 0.25 × speed, where speed = 1 − min(t_elapsed, 30min) / 30min over the whole test set.
  • Qualifier deadline was 24 May 2026 23:59 SGT. AE is closed; only Semifinals/Finals matches remain.

Inputs and outputs (schema)

Every /ae POST contains a list of observations under instances. Each observation is a dict with at least:

{
  "step": int,                   // current game tick (0 means new round → /reset)
  "location": [x, y],
  "direction": int (0..3),
  "health": int (0..60),
  "base_health": int (0..100),
  "team_bombs": int,             // remaining bombs in our team stockpile
  "agent_viewcone": [[...], ...], // 7×9 channels, viewport around agent
  "base_viewcone": [[...], ...],  // 11×11 channels, viewport around our base
  "action_mask": [0/1, ...]       // length 6, which of our 6 actions are legal
}

Actions: FORWARD=0, BACKWARD=1, LEFT=2, RIGHT=3, STAY=4, PLACE_BOMB=5.

The action_mask is enforced. Illegal actions no-op. The server's response must be {"predictions": [{"action": int}]} — wrong JSON shape scores 0 even with a perfect model.

The Novice map

The qualifier round uses a single fixed map ("Novice"). We pre-baked the wall layout, destructible walls, base locations, and starting item coordinates into ae/src/novice_map_data.py so the agent can plan on it without needing to discover the layout from observations.

The six possible base locations are [13,9], [9,13], [3,12], [2,6], [6,2], [12,3]; the six matching starting locations are [14,9], [9,14], [3,11], [2,7], [6,3], [12,4]. Each round randomly assigns one of the six slots to our team.

2. Terms and concepts (so the rest reads cleanly)

Heuristic / AEManager
Our hand-coded planner agent (ae/src/ae_manager.py, ~2050 lines). Maintains a memory of the map, tracks visible enemies and bombs, computes danger cells, and at each tick scores candidate target cells (enemy bases, items, frontier cells, defensive cells), picks the best, paths to it via Dijkstra or BFS, and chooses an action.
Heuristic-A / heuristic-B / heuristic-C
Three named hand-tuned env-var configurations sweep-tested during the 24 May qualifier cycle. A = aggressive offense (AE_ENEMY_BASE_VALUE=160, AE_DIST_PENALTY=0.9). B = defense-first (AE_TIER1_DEFENSE=1, larger defense radius/health). C = item farming (AE_ITEM_MISSION_VALUE=80, AE_ITEM_RESOURCE_VALUE=40, AE_ENEMY_BASE_VALUE=100).
PPO
Proximal Policy Optimization — the policy-gradient RL algorithm we use to fine-tune neural agents in training/ae/train_ppo.py. Multiple PPO recipes were trained over the qualifier cycle (ppo-full-rl-v1, ppo-qualifier-best-v1..v4, belief-v1, elo-v1, hybrid-friend-v1); all of them landed cloud at ~0.41–0.47, well below the heuristic's 0.55–0.64 band.
BC (Behavior Cloning)
Supervised imitation training: collect (obs, action) trajectories from the heuristic, then train a neural policy with cross-entropy to predict the heuristic's actions. The result (bc.pt) is a starting point for PPO, never deployed by itself.
HybridAEManager
Decision wrapper: runs the PPO policy first, but vetoes it with the heuristic when the policy's choice is "obviously" wrong (frozen-STAY, low confidence, MCTS-light disagrees). Several runtime modes exist via the AE_MODE env var: hybrid (default policy+veto), policy (pure policy), heuristic (pure planner), option_hybrid (8-way learned macro selector), tactical_hybrid (12-way macro selector), and the new scripted_hybrid (this session).
Heuristic fallback
Every hybrid path is wrapped in try: load policy except: return AEManager() in ae_server.py. This is the bug that caused the 0.638 cloud "PPO" submission to actually be heuristic. See history below.
Furnished gate / cloudsuite / pressure2 / bracket_proxy / etc.
Local opponent "suites" defined in training/ae/opponents.py. Each suite is a 5-tuple of opponent classes (Hunter, Rusher, Bomber, etc.) used as the other 5 teams in local evaluation. The "furnished gate" is the canonical 8-suite weighted mean in validate_cloud_suite.py: cloudsuite 0.18, pressure2 0.18, strong_realistic 0.20, base_rush_exploit 0.18, bracket_proxy 0.14, top_seed_proxy 0.08, defense_trap 0.04, mixed 0.04. The weights approximate the cloud opponent distribution.
PYTHONHASHSEED
A Python env var that controls the hash function's random salt. Without it set, dict and set iteration order varies across runs. Our AEManager has hash-order-dependent branches in candidate scoring; unpinned PYTHONHASHSEED makes identical (env, seed, rounds, suite) triples drift by 0.10+ on cloudsuite mean across runs. We now auto-pin it to 0 at the top of every entry point and bake ENV PYTHONHASHSEED=0 into the Dockerfile.
Multi-seed eval / n=5
Our new gold-standard local gate: multi_seed_eval.py spawns one validate_cloud_suite.py subprocess per (hash_seed, sim_seed) pair (e.g., 5 hash seeds × 1 sim seed = 5 independent runs), then aggregates per-suite mean ± SE. A single pinned-hash run gives one realization; n=5 approximates the hash-distribution average that cloud submissions sample from.
Harm-aware gate
An inference-time gate on the 12-way tactical option selector. Instead of admitting any transition that has ≥N positive samples in the training data (the legacy gate), the harm-aware gate also checks the positive rate (positives / attempted) and mean net delta per transition. We added per-transition attempted / positive / negative / net_delta_sum matrices to the collector + trainer + manager.
Orientation-aware A*
Dijkstra search over (x, y, facing) states with a configurable turn cost. The default Dijkstra in our manager treats LEFT/RIGHT turns as free, so a path with 3 turns + 5 forward steps is reported as 5 cost even though it actually takes 8 game ticks. Orientation-aware fixes that. Opt-in via AE_ORIENTATION_AWARE_PATH=1.
M5
The codename of another team's scripted-policy architecture, summarized in a doc shared with us (M5_SUMMARY.md). Their ScriptedBaseAttackPolicy uses orientation-aware A*, a spawn-aware first-target table, enemy-bomb-only escape, tactical cluster bombing, single-blocker bombing when stuck, and own-base defense routing — all chained as a primary policy with BC + heuristic as fallbacks. They reportedly scored ~0.731 cloud, vs our 0.638 max. We ported every piece this session to test whether the lift is portable. (Spoiler: it isn't.)
Pandemonium
Another team that reportedly hit 0.731. Their plan documents (4 files shared with us) describe generic Stable-Baselines PPO + a BFS rule-based fallback. The PPO part doesn't reproduce; the durable lesson is "scripted-first arbitration with learned high-level choices, not pure neural control" — same direction as M5.

3. Our agent's architecture

Decision flow at one tick

For the default AE_MODE=hybrid path:

  1. HTTP server (ae_server.py) receives {"instances": [{"observation": {...}}, ...]}. If observation.step == 0, calls /reset first (re-instantiates the manager — no persistent state outside the manager).
  2. Manager dispatch: reads AE_MODE env var, instantiates the matching manager class. Each one degrades gracefully to AEManager() if it fails to load (the silent-fallback bug).
  3. Per-tick (manager.ae(observation)): parse observation → update memory → compute danger cells → pick a target (enemy base / item / defense / frontier) → BFS or Dijkstra path → translate to action → return int.

Modes

AE_MODEWrapper classBehavior
heuristicAEManagerPure rule-based planner. No torch, fastest. Cloud max 0.612 (intentional, n=14).
hybrid (default)HybridAEManagerPPO policy + heuristic safety veto + frozen-STAY guard + top-K cascade.
policyPolicyAEManagerPure PPO policy (no veto).
option_hybridOptionHybridAEManager8-way learned macro selector (escape/rush/farm/hunt/explore) with planner execution.
tactical_hybridTacticalHybridAEManager12-way learned tactical selector with planner execution. The "semifinals path" until this session.
scripted_hybrid (new this session)ScriptedHybridAEManagerM5-style scripted policy first; heuristic fallback. -3.35σ on furnished gate.

Key AEManager subsystems

  • Memory: self.seen (set of explored cells), self.walls / self.destructible (edges), self.last_seen_items (dict pos → (kind, step)), self.enemy_agents (dict pos → step), self.known_bombs (dict pos → {timer, own}), self.enemy_bases.
  • Pathfinding: _bfs_distance_map(start, danger) for general maps; _dijkstra_distance_map(start, danger) for fixed-novice (handles destructible walls with a configurable bomb cost). New this session: _orientation_aware_distance_map(start, facing, danger) over (x, y, facing) states.
  • Target scoring (_choose_target): for each candidate cell, compute value − DIST_PENALTY × distance − 0.25 × visit_count − PATH_THREAT_PENALTY × threats_on_path. Top score wins.
  • Danger / escape: _danger_cells() = union of blast cells from bombs with timer ≤ 2. _active_escape_path() handles in-progress escape from own bomb's blast.
  • Bombing: _should_place_bomb() returns true when a bomb here would damage an enemy base, kill an enemy, or clear a destructible wall on our path, AND we have a guaranteed escape path before detonation.

The silent-fallback discovery (24 May)

Critical finding from 24 May: every 0.55–0.64 "PPO" or "hybrid" cloud submission from 22–24 May was actually serving pure heuristic. Forensic git-diff showed ae/src/model.py at commit c66a4b7 (the May 22 deploy) didn't contain LegacyPolicyNetwork. Loading ppo-full-rl-v1.pt (legacy-small architecture) raised a shape-mismatch error in policy_manager._load_model. The except Exception: return AEManager() clause in ae_server.py silently caught it. Container booted, served heuristic, scored 0.55–0.64 — matching the historical ae-fixed-map-v5 heuristic baseline. When the May 24 Elo experiment re-added legacy support, the policy actually engaged for the first time and cloud scores immediately collapsed to ~0.41.

Why the PPO ceiling is real

Four independent PPO recipes have hit the same ~0.41–0.47 cloud band: ppo-full-rl-v1, elo-v1, belief-v1, hybrid-friend-v1. Each was warm-started differently, trained against different opponent pools (random / scripted / cloudsuite / league / mixed), and used different exploration / curricula. None broke through. The local→cloud transfer gap is the binding constraint: local proxies improve while hidden eval doesn't, because the learned policy optimizes the local opponent/shape distribution.

The 24 May calibration finding

A methodology audit on 24 May evening tried to find a local eval suite whose rankings predict cloud rankings. Result: we cannot. Two reasons:

  1. PYTHONHASHSEED was unpinned. Same (env, seed, rounds, suite) triple drifted by 0.10+ on cloudsuite mean across runs of unpinned interpreters. Every sweep before that evening was reading hash noise on top of signal.
  2. Local opponents under-represent cloud's distribution. Re-running 9 env-knob perturbations on cloudsuite at PYTHONHASHSEED=0: 4 distinct config combos all yielded identical local cloudsuite scores. Cloud separates them by 0.04. Our local rusher/hunter/bomber pool doesn't activate the code paths that matter on cloud.

Semifinals positioning (26 May)

We finished 15th on the Novice path leaderboard. Expected semifinals Match 1 bracket is seeds 3/8/9/14/15/20 — bracket-shape opponents, not the mass-bomb chaos suites. This is what motivated today's work: AE is the most movable lever to win Match 1 outright, and bracket-shape suites are different enough from the qualifier cloud distribution that some primitives may help even if they didn't on the qualifier gate.

6. W1 — methodology infrastructure (shipped first)

W1.2 — PYTHONHASHSEED auto-pin

Patched 6 entry points and the Dockerfile. The pattern at the top of each script:

import os, sys
if os.environ.get("PYTHONHASHSEED") is None:
    os.environ["PYTHONHASHSEED"] = "0"
    os.execvp(sys.executable, [sys.executable, *sys.argv])

Note the check is is None, not != "0" — that way the multi-seed eval can explicitly set PYTHONHASHSEED=1, =2 etc. and the auto-relaunch doesn't fight back.

Files patched: validate_cloud_suite.py, simulate.py, sweep_heuristic_knobs.py, sweep_option_v2.py, compare_candidates.py, collect_tactical_outcome.py, and ae/Dockerfile.

W1.1 — Harm-aware tactical gate

The existing 12-way tactical option selector had a legacy gate: admit a transition only if it has ≥AE_TACTICAL_MIN_DELTA_SUPPORT positive samples in training data. Problem: when we doubled the dataset from 400 to 800 games, the absolute count threshold became implicitly looser, and the new checkpoint regressed on bracket-relevant suites because some transitions had many positive samples but a low positive rate.

The fix is to track per (prior_option, option) transition:

  • attempted: total times the exploration policy chose this transition (positive + negative + neutral)
  • positive: times the episode delta was > min_positive_delta
  • negative: complement
  • net_delta_sum: sum of episode deltas
  • Same triple by distance bucket (near ≤ 4 / mid ≤ 8 / far > 8)

Then at inference, gate by attempted ≥ AE_TACTICAL_MIN_ATTEMPTED AND positive / attempted ≥ AE_TACTICAL_MIN_POSITIVE_RATE AND net_delta_sum / attempted ≥ AE_TACTICAL_MIN_NET_DELTA. All defaults preserve byte-equivalent legacy behavior when unset.

Code path: collector (collect_tactical_outcome.py) → trainer (train_tactical_bc.py) → checkpoint .pt → manager (tactical_hybrid_manager.py).

The harm-aware finding: tactical-hybrid line is dead

I ran a fresh 800-game collection with the new metadata. Result: 160,000 sample transitions across 90 distinct (prior, option) pairs — ZERO with positive expected delta. The most positive-direction transition was hunt_visible_enemy → collect_mission_safe at 12.9% positive rate, mean_delta = -0.153. Every single transition is net-harmful in expectation under random tactical exploration.

Our heuristic beats random tactical exploration on the 12-way macro grid. The 26 May 400-game tactical_policy.pt "working" at the 0.85/50 legacy gate was variance — the legacy gate let in transitions that had ≥50 positive samples even though their rate was abysmal.

7. W2 — M5 architecture experiments

Plan: port M5's primitives one at a time (W2.1), and if individual primitives didn't lift, port the whole ScriptedBaseAttackPolicy as a primary policy with our AEManager as fallback (W2.2).

W2.1 — three M5 primitives bolted on

Why W2.1a regressed

The first-target boost added 60.0 to specific enemy bases, which interacts with DIST_PENALTY=1.15 to commit the planner harder to a distant target. Without orientation-aware A*, that means more wasted ticks on a longer route. (The M5 doc itself says the primitives are synergistic.)

Why W2.1b mostly regressed despite looking right on paper

Our existing _danger_cells() already treats timer ≤ 2 bombs as danger. The M5 difference is that the override fires before any other action selection, forcing escape behavior. In bracket scenarios that's correct (top_seed_proxy +0.124 smoke result), but in mass-bomb chaos (pressure2), reacting to every short-lived threat costs more tempo than just walking through. The n=2 smoke result's apparent bracket lift was variance — n=5 collapsed it to -0.031.

Why W2.1c at turn_cost=1.0 was catastrophic

Our DIST_PENALTY is tuned for grid distance (1 cell = 1 unit). Adding real turn costs makes "1 cell + 2 turns = 3 units" — effectively triples the penalty for misaligned targets. The planner stops picking those targets even when they're worth more, and ends up in target loops. Dropping to turn_cost=0.3 recovered most of the damage but the per-suite pattern stayed: bracket suites slightly win, defense/pressure suites slightly lose.

W2.2 — full ScriptedBaseAttackPolicy port

New file ae/src/scripted_base_attack.py (~330 lines) implementing the full M5 decision tree:

  1. Enemy-bomb escape (W2.1b reuse, forced on for scripted path)
  2. Bomb from attack square (when committed and at target with PLACE_BOMB legal)
  3. Tactical cluster bombing: ≥2 visible enemies in blast, not already covered by an ally bomb, has escape
  4. Single-blocker bombing: exactly 1 enemy in blast AND stuck/looping (M5's 4 conditions)
  5. Own-base defense: bomb threat in place if doesn't hit our base; else route to defensive bomb square if cost ≤ 7.5
  6. Continue committed attack route (orientation-aware A* when enabled)
  7. Pick new attack plan: per active enemy base × every reachable cell whose blast contains the base, score = route_cost + 2·rank_penalty + 0.25·visit_count + 0.05·distance_from_own_base; lowest wins
  8. Decline → fallback to AEManager.ae()

The wrapping scripted_hybrid_manager.py runs AEManager.ae() first (for memory sync), then calls scripted.act(); if scripted returns None or raises, returns the heuristic action.

9. Final operational recommendation

For the next cloud submission round, deploy this configuration:

AE_MODE=heuristic
AE_ITEM_MISSION_VALUE=80
AE_ITEM_RESOURCE_VALUE=40
AE_ENEMY_BASE_VALUE=100
AE_DIJKSTRA_BOMB_COST=7.0
# Plus existing Dockerfile defaults:
#   PYTHONHASHSEED=0
#   AE_TIER1_REPEAT_KILL=1
#   AE_TIER1_NO_STAY_PENALTY=1
#   AE_TIER1_PREDICTIVE_WALK=1

Local n=5 weighted mean: 0.2842 ± 0.0074 vs baseline 0.2640 ± 0.0162 (Δ +0.020, +1.13σ).

Expected cloud performance

Cloud per-config σ ≈ 0.024 (established from n=5 fresh baseline samples on 24 May). With our local +1.13σ above baseline and baseline's historical cloud mean around 0.56–0.58, the expected cloud mean for this combo is ~0.59–0.60. Upper-tail draws can plausibly hit 0.64+ within ~5 submits — enough to potentially match or beat the historical 0.638 high.

Variance-farming strategy

If we have N submits available:

  • Spend ~70% on the combo (C + bomb=7.0) — it's the highest-mean config we have.
  • Spend ~20% on heuristic-C alone (different upper-tail mechanism — extra mission/resource collection)
  • Spend ~10% on bomb_cost=7.0 alone (different upper-tail mechanism — better bomb-blast routing)
  • Don't variance-farm a single config 10+ times. Within-config σ ≈ 0.024 means <10% chance of beating historical upper-tail draws per realistic budget.

What NOT to do

  • Don't enable any of W2.1a/b/c flags or W2.2 scripted_hybrid. They all lost at the calibrated gate. They stay in tree as default-off, documented negative results.
  • Don't start a new PPO training line. Four recipes have hit the same ~0.41–0.47 cloud ceiling. The local→cloud transfer gap is genuinely structural.
  • Don't run broad/blind heuristic sweeps. Screens with single-seed n=8 (the prior pattern) produce false peaks that don't survive paired multi-seed gates. We have evidence: bridge_0211, focus_0124, option_grid_*, dypm-veto promotion gates all failed this way.
  • Don't promote on single-seed results. The W2.1b 4-round × 2-hash smoke showed +0.124 on top_seed_proxy; n=5 collapsed it to −0.031. Always run n≥5 hash seeds before believing a Δ.

11. For next year

What we learned that's actually durable

  1. Pin PYTHONHASHSEED from day one. The amount of analysis we did on hash-noised sweeps before catching this on 24 May is embarrassing. Make it the first thing the harness does on a fresh checkout.
  2. Within-config cloud σ ≈ 0.024. Any A/B with fewer than 5 cloud submissions per config is barely better than n=1 for ranking. Don't make irreversible decisions on 3-submit means.
  3. Local→cloud transfer is real and binding. Multiple PPO recipes hit a hard ~0.47 cloud ceiling while local eval climbed to 0.66+. The local opponents don't activate the same code paths as cloud.
  4. Multi-seed eval is the way. Single-seed n=8 produces false peaks (we have a dozen historical examples). Always spawn K×M hash×sim subprocesses and report mean ± SE.
  5. Harm-aware gates beat count-only gates for any imitation/exploration setup. The 12-way tactical setup looked promising on count-only support; harm-aware data falsified it definitively.
  6. Don't bolt on M5 (or any other team's) primitives one at a time. The whole architecture or nothing. Individual primitives are calibrated against the rest of their codebase, not ours.
  7. Operationally: re-rank existing configs before chasing new ones. The biggest score lift today came from realizing heuristic-C was already best and combining it with another existing knob. Six hours of M5 porting yielded no lift; one calibrated re-ranking + combo test produced +1.13σ.

If AE reopens for Finals

The first 30 minutes of work should be:

  1. Verify PYTHONHASHSEED=0 is still in the Dockerfile and entry points (regression risk on any rebase).
  2. Re-run multi_seed_eval.py on the combo to confirm it still beats baseline at the new opponent distribution (if Finals uses different suites).
  3. Spend cloud budget on the combo per the variance-farming strategy in §9.

Only after that, if there's time and budget, consider the deeper open questions:

  • Why does cluster_bomb fire often locally but score zero cloud A/B effect? Diagnostic: instrument cluster-bomb fire rate per round per cloud submission.
  • Is the defense_trap +0.07 from bomb_cost=7.0 real or an artifact of the 4%-weight on that suite? Higher-rounds eval would resolve.
  • Could a harm-aware gate on the W2.2 scripted_hybrid policy salvage it? The skeleton-only was -1.21σ; if specific scripted rules are toxic and we knew which, we might recover.
